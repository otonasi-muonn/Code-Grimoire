## 🔴 必須対応 (展示までに修正)

### 1. Worker 初期化失敗時の UI 永続ローディング

**ファイル**: `src/webview/core/worker-bridge.ts:109-111`
**出典**: Agent #1 (bug-hunter)
**検証**: ✅ Read で実物確認済み

**コード現状**:
```typescript
.catch(err => {
    console.error('[Code Grimoire] Worker init failed:', err);
});
```

**症状**: Worker JavaScript の `fetch` (`workerUrl`) が CSP 制限 / ネットワーク遮断 / Worker bundle 不在等で失敗すると、`state.isLoading = true` のまま、loading overlay も hide されず、UI が永遠にローディング表示。ユーザーは原因不明で「壊れた」と感じる。

**再現条件**:
- ビルドミス (`out/webview/worker.js` 不在) で `fetch` が 404
- VS Code Webview の CSP が `blob:` を拒否する将来バージョン
- 拡張インストール失敗で worker.js が抜けた状態

**深刻度**: 🔴 致命的 (UI 完全固まり、ユーザー操作不能)

**修正方針**:
```typescript
.catch(err => {
    console.error('[Code Grimoire] Worker init failed:', err);
    // recoverFromError が closure 外なので、初期化失敗時の復旧をここで明示
    state.isLoading = false;
    callbacks.stopParticleLoading();
    callbacks.updateStatusText();
    // 任意: UI にエラー通知を表示する DOM 操作を追加
});
```

### 2. PixiJS WebGL/Canvas2D サイレントフォールバック

**ファイル**: `src/webview/main.ts:198-206`
**出典**: Agent #10 (devils-advocate)
**検証**: ✅ Read で実物確認済み

**コード現状**:
```typescript
await app.init({
    background: 0x080a18,
    resizeTo: window,
    antialias: true,
    resolution: window.devicePixelRatio || 1,
    autoDensity: true,
});
```

**症状**: PixiJS v8 のデフォルト renderer 選択は **WebGL → WebGPU → Canvas2D の順でサイレントフォールバック**[^1]。展示マシン (会場提供 PC など) で WebGL が利用不能の場合、自動的に Canvas2D に落ちる。`preference` を明示していないため、開発者・ユーザーともに「Canvas2D で動いている」事実に気づかない。

**展示インパクト**: 提出済みイベントデータの謳い文句「**PixiJS による魔法陣 WebGL 描画**」が事実と異なる状態で展示される可能性。

**深刻度**: 🔴 高 (謳い文句の信頼性崩壊)

**修正方針** (2 ステップ):
```typescript
// 1. WebGL を明示優先
await app.init({
    preference: 'webgl',  // ← 追加
    background: 0x080a18,
    // ...
});

// 2. 実際の renderer 種別をログ + 必要なら画面隅にバッジ
console.log('[Code Grimoire] Renderer:', app.renderer.type); // 'webgl' or 'webgpu' or 'canvas'
if (app.renderer.type === 'canvas') {
    // 開発者注意: Canvas2D fallback 発生
}
```

[^1]: PixiJS v8 公式 [Renderers](https://pixijs.com/8.x/guides/components/renderers) (Tier 1)

## 🟡 推奨対応 (展示後でも許容)

### 3. PixiJS Graphics の `destroy()` 漏れ

**ファイル**: `src/webview/renderer/graph.ts:450-484` (新規追加: `hugeWarnRing` / `hugeCriticalRing` / `cycleRing` / `hotRing`)
**出典**: Agent #4 (パフォーマンス), Agent #10 (devils-advocate)
**検証**: ✅ Read で実物確認済み

**症状**: 新規 Graphics オブジェクト (hugeFileLevel リング・severity 表示・isHotSpot 二重リング) が `renderGraph()` 呼び出しのたびに生成され、destroy されない。`container.removeChildren()` だけだと PixiJS 内部の texture/buffer はガベージコレクト依存。

**再現条件**: 1k+ ノードで renderGraph を頻繁に呼び出す (rune mode 切替 / layout mode 切替 / 解析再実行) → 数十 MB ずつメモリ増加。展示中数時間運用で 100MB-1GB のリーク可能性。

**深刻度**: 🟡 中 (展示が数時間なら顕在化、即時クラッシュは稀)

**修正方針**:
```typescript
// renderGraph 内 / リフレッシュ前に
nodeContainer.children.forEach(child => child.destroy({ children: true }));
nodeContainer.removeChildren();
```

CLAUDE.md §7 「PixiJS Graphics の `destroy()`: renderGraph 再呼び出し時のメモリリーク対策」に既に明記されているルール違反。

### 7. SecurityWarning.severity 必須化の後方互換

**ファイル**: `src/shared/types.ts:128-144`

## 反証された指摘 (エージェント間矛盾の整理)

### ❌ 「ripgrep 例外時に SEARCH_CONTENT_RESPONSE が届かない」 (Agent #1)

**反証**: `src/ripgrep-search.ts:44-123` を Read 確認。`runRipgrepSearch` は **常に `resolve()` する設計** で、`reject()` は一切呼ばない。spawn 失敗・rg バイナリロード失敗・パースエラー全て `resolve({ matches: new Set(), ... })` でフェイルセーフ。

→ Agent #1 の指摘は **コードの誤読**。`extension.ts:219` の `await` も throw しない。

### ⚠️ 「v0.1.2 → v0.2.0 ユーザーキャッシュ破壊」 (Agent #6)

**部分反証**: `extension.ts:35` の `cachedGraph` は **module-level let で永続化なし**。VS Code 拡張プロセス終了で消える。`globalState` には GraphNode 系を保存しないため、v0.1.2 ユーザーがアップデート時に「古い severity なしの SecurityWarning」を読み出すルートは存在しない。

→ TypeScript 型システム上の問題のみで、ランタイム互換性破壊は限定的。

### 🤝 「Tarjan 再帰の深さ問題」 (Agent #10) vs 「Tarjan 完全保持で退行なし」 (Agent #2)

**両者矛盾せず**: Agent #2 は「アルゴリズム自体は教科書通り保持」、Agent #10 は「実装方式 (再帰) が深いチェーンで限界」を別レイヤで指摘。両論併記。

### 🤝 「PixiJS Canvas2D fallback リスク」 (Agent #10) vs 「WebGL 描画は問題なし」 (Agent #2)

**Tier 1 公式ドキュメントで Agent #10 採用**: PixiJS v8 公式 [Renderers](https://pixijs.com/8.x/guides/components/renderers) で WebGL → WebGPU → Canvas2D フォールバックが標準動作と明記 (Tier 1)。`preference` 未指定はリスク。
