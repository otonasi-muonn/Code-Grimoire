# 3 レイアウト (宇宙) ガイド

> Code Grimoire は同じ依存グラフを 3 通りのレイアウトで配置できます。**5 ルーン × 3 レイアウト = 15 通り**の組み合わせで、同じコードベースを多角的に「読む」「巡る」体験を作ります。

切替キーは **Q / W / E** (順に Mandala → Galaxy → Bubble)。

---

## 早見表

| キー | レイアウト | 描画原理 | 強み | 苦手 |
|-----:|-----------|---------|------|------|
| Q | **Mandala** (魔方陣) | d3-force 物理シミュレーション (Web Worker 内) | 密結合クラスタの自然形成、依存の重力中心が見える | 「正解の位置」が定まらず、毎回少し違って見える |
| W | **Galaxy** (銀河) | エントリーポイント中心 + BFS 深度で同心円 | 中心 = コアロジック / 外周 = 末端 / 最外周 = 到達不能 (デッドコード) の構造把握 | 大規模で末端ノードが圧縮されすぎる |
| E | **Bubble** (泡宇宙) | ディレクトリ階層を入れ子円で表現 | フォルダ構造そのものを可視化、子ディレクトリの「責務の散らばり」が見える | ファイル間の依存は薄い線で表現、edge ベース解析には不向き |

---

## Q. Mandala (魔方陣)

### 描画原理
- d3-force の物理シミュレーションを **Web Worker** で動かす。
- ノード同士は引力 / 斥力で位置を決め、依存関係 (edge) が強いほど近づく。
- メインスレッドはレイアウト計算をしないため、ノード数が増えても 60fps を維持する。

### 何が見えるか
- **密結合クラスタ**: 互いに import し合うファイル群が自然に塊を作る → モジュールの「重力中心」
- **孤立ファイル**: 誰とも依存していないファイルが端に押し出される
- **フォーカスノードの近隣**: focus ring に集まり、context ring に少し離れた依存先、global ring にその他

### 強み
- 設計が綺麗なコードベースほど、クラスタが綺麗に分離して見える。「フォルダ構造と依存構造が一致しているか」が一目で分かる。
- ノードクリック (Summoning) で focus が変わると、世界がふわりと再配置される演出が美しい (展示映え)。

### 苦手
- 確定的な配置ではない (毎回少し違う) ため、「あのファイルどこだっけ?」という再現性は弱い。
- 1000+ ノードになると初回収束まで時間がかかる (WARMUP_TICKS=300)。

### おすすめのルーン組み合わせ
- **default × Mandala**: フォルダ構造と物理クラスタを見比べる
- **architecture × Mandala**: 循環参照ノードが束で見える
- **analysis × Mandala**: edge 色付きで「データの流れ」を立体的に見る

---

## W. Galaxy (銀河)

### 描画原理
- エントリーポイント (もっとも outgoing 依存が多いファイル、または現在のフォーカスノード) を中心に配置。
- そこから BFS で深度を計算し、深度 1 のファイルは内側のリング、深度 2 は次のリング、...と同心円状に並べる。
- どこにも到達できないノード (孤立) は **最外周 (追放の地)** に置かれる。

### 何が見えるか
- **中心 = コアロジック**: エントリーポイントから直接 import される
- **内側のリング = 主要モジュール**: 浅い依存で繋がる
- **外側のリング = 末端**: 深い依存チェーンの先
- **最外周 = デッドコード候補**: エントリーポイントから到達不能なファイル群

### 強み
- 「このファイル、本当に使われてるんだっけ?」を最外周で即判別できる。Orphan 検出。
- 中心からの距離 = 重要度の直感的な対応付けが効く。

### 苦手
- 同心円配置のため、ノード数が多いと末端リングが詰まって読みにくい。
- エントリーポイントが複数ある場合 (`bin/`, `src/index.ts`, テスト entry など)、どれを中心にするかで見え方が大きく変わる。

### おすすめのルーン組み合わせ
- **default × Galaxy**: 「コアと末端」の関係を俯瞰
- **architecture × Galaxy**: 循環参照が外周で巻いていると怪しい
- **optimization × Galaxy**: 最外周 (デッドコード候補) + tree-shaking リスクで Orphan を特定

---

## E. Bubble (泡宇宙)

### 描画原理
- ディレクトリ構造を **入れ子の円 (泡)** で表現。
- d3-hierarchy の pack レイアウトでフォルダ円を配置、ファイルは所属フォルダの中に配置される。
- ファイル円のサイズはツールバーで切替可能: **📏 行数** または **📦 ファイルサイズ**。
- フォルダ円自体に **凝集度ヒートマップ** (T-06): cohesion / avgLineCount / cycleCount のメトリクスで縁取り色が変わる。

### 何が見えるか
- **フォルダ構造そのもの**: `src/components/Button/Button.tsx` がどう入れ子になっているか
- **責務の散らばり**: 1 つの機能が複数フォルダに散乱していると、依存線がフォルダ円を多数横切る
- **フォルダの大きさ**: 子ファイル数 × サイズで bubble の大きさが変わる
- **凝集度メトリクス**: 緑 = 高凝集 / 黄 = 中 / 赤 = 低凝集

### 強み
- フォルダ階層が直感的に伝わる。「設計の癖」を見るならまずこれ。
- 子ファイルが一塊になることで「このフォルダの責任範囲」が一目で分かる。
- フォルダクリックで折りたたみ / ドリルダウンが可能。

### 苦手
- 個別の依存線 (edge) は薄く描かれるため、edge ベースの解析には向かない。
- 階層が深い (10 層超え) と内側の bubble が小さくなりすぎる。
- bubble label は LOD `mid` 時のみ表示 (ズームアウト時はフォルダ名見えず)。

### おすすめのルーン組み合わせ
- **default × Bubble**: フォルダ構造の俯瞰、これが基本形
- **architecture × Bubble**: フォルダ単位の cycleCount メトリクスで「循環の多いフォルダ」が赤くなる
- **optimization × Bubble**: 大きいフォルダがどこにあるか、avgLineCount で「肥大フォルダ」を発見

---

## レイアウトの使い分けフロー

| 知りたいこと | おすすめレイアウト |
|------------|-----------------|
| フォルダ構造、責務の散らばり | **Bubble** (E) |
| ファイル同士の物理的な結びつき、クラスタの自然形成 | **Mandala** (Q) |
| エントリーポイントからの依存深度、デッドコード候補 | **Galaxy** (W) |
| 循環参照の **存在** をパッと判定 | **Mandala × architecture** (Q + 2) |
| 循環参照を **持つフォルダ** を特定 | **Bubble × architecture** (E + 2 + cycleCount metric) |
| 危険関数の散らばり | **Mandala or Galaxy × security** |

---

## 共通のパフォーマンス特性

- レイアウト計算は **Web Worker** に隔離されているため、メインスレッドの 60fps は維持される (パンフレット謳い文句通り)。
- レイアウト切替 (Q → W → E) 時、Worker が一旦アイドルになって新規計算に入るので 1-2 秒の "warming up" 期間がある。
- LOD: ズームアウトすると `far` モードに自動切替、ノードが簡略化され FPS を確保。
