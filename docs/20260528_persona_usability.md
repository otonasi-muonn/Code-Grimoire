### #15 の処方箋への重大な反論 (Tier 1 ソース付き)
20 体の #15 (PixiJS) は「morph で全 Container を destroy→再生成は無駄、position.set で済む」と指摘。**事実 (TICK×40 回 destroy) は真**だが、**処方箋は危険**:
- PixiJS v8 公式は「destroy は GPU リソースを即時解放し**リークを減らす**」と明言
- destroy をやめたことによる 10MB/s リーク→数分でクラッシュの実例が公式 Issue [#10549](https://github.com/pixijs/pixijs/issues/10549) / [#10586](https://github.com/pixijs/pixijs/issues/10586) に存在 (Tier 1)
- `graph.ts:211` のコメント「長時間運用 (展示・常駐) のリーク対策」は、この罠を踏んだ上の**意図的判断**の可能性が高い
- → 「position.set に単純書き換え」を採用すると展示クラッシュリスク。やるなら「morph 中のみ destroy スキップ + DONE 時に一度だけ完全再構築」だが、**展示 2 日前のこの書き換えは高リスク**。実測して許容範囲なら触らない (YAGNI)

### セキュリティ指摘 (#10) の誇張補正
devils が Read で確認: 危険関数判定は `getText()` 単純比較**だけではない**。`callText === df.pattern || callText.endsWith('.' + df.pattern)` + JsxAttribute/PropertyAccess/BinaryExpression の AST 判定を併用。`obj.eval` は拾う。「文字列比較のみ=雑」は誇張。`obj['eval']` 取りこぼしは真だが、展示でデモするのは自前サンプルなので発火しない。

## 20 体全員が見落とした盲点 (devils-advocate の最大の貢献)

**展示会場の物理制約** — これが本来の優先度 1 位:
- **オフライン動作**: `worker-bridge.ts:55` で `fetch(workerUrl)`、CSP は `img-src https:` 許可。会場 Wi-Fi が死んでも動くか未検証なら単一障害点
- **会場 PC の GPU/WebGL**: PixiJS は WebGL 必須。貸出 PC やリモートデスクトップ展示だと WebGL 無効で真っ黒。`preference: 'webgl'` 明示済だが、フォールバック挙動は未検証
- **VS Code バージョン**: `engines.vscode: ^1.100.0`。会場 PC が古いと拡張が起動すらしない
- **vsix 配布動線**: 会場 PC にどう拡張を入れるか (Marketplace 非公開なら手動 vsix)
